# Emuera.Headless 架构评估报告

## 一、架构总览

当前项目已完成与 WinForms 老项目的物理分离，形成了 **四层架构**：

| 层级 | 目录 | 职责 |
|------|------|------|
| 入口层 | `Program.cs` / `HeadlessOptions.cs` / `ServerRunner.cs` | CLI 参数解析、模式路由 |
| 协议层 | `Agent/` | Agent 协议抽象（CLI VT / JSONL），回合驱动 |
| 适配层 | `Headless/` + `Primitives/` | IConsoleUI 空实现、GDI 类型替换 |
| 游戏引擎层 | `Shared/` + `UI/Game/` | EmueraConsole 核心逻辑（共享自原项目） |

服务器模式通过 `Server/` 子系统以 HTTP 长轮询暴露 JSONL 协议，由 `Session` → `AgentJsonlProtocol` → `EmueraConsole` 串联。

**总体判断：架构基础扎实，分层清晰，但存在若干跨平台硬伤和可扩展性瓶颈需要解决。**

## 二、分项评估

### 2.1 模块化程度：★★★★☆（良好）

**优势：**
- **协议抽象干净**：[AgentProtocolBase](../../EraCore.Core/Agent/AgentProtocolBase.cs#L9-L99) 采用模板方法模式，`GetInitialTurnAsync` / `StepAsync` / `SubmitTimeoutAsync` 定义了清晰的回合协议契约，CLI 和 JSONL 两条路径完全解耦
- **IConsoleUI 抽象到位**：[HeadlessConsole](../../EraCore.Core/Headless/HeadlessConsole.cs#L10-L50) 作为 IConsoleUI 的空实现，成功隔离了 WinForms 依赖，所有操作返回合理默认值
- **IO 抽象可插拔**：[SessionIO](../../EraCore.Core/Server/SessionIO.cs#L10-L20) 抽象了 stdin/stdout，[HttpSessionIO](../../EraCore.Core/Server/HttpSessionIO.cs#L12-L90) 基于 Channel 实现，替换传输层无需触碰协议逻辑
- **自定义值类型**：`Primitives/` 下的 `EmuColor`/`EmuPoint`/`EmuRectangle` 等彻底移除了 `System.Drawing.Common` 依赖（csproj 注释确认）

**问题：**
- **EmueraConsole 是上帝对象**：[EmueraConsole.cs](../../EraCore.Core/UI/Game/EmueraConsole.cs#L20-L200) 701 行，直接暴露 `_state` 的 30+ 属性，既有状态查询又有输入/打印/生命周期方法，职责过多。虽已拆出 `_stateManager`/`_printManager`/`_inputHandler` 等子对象，但对外仍是一个巨大门面
- **GlobalStatic 进程级单例**：[GlobalStatic.cs](../../EraCore.Core/GlobalStatic.cs#L26-L239) 9 个核心字段用 property + lock 断言保护，`Reset()` 支持会话重置，但本质仍是进程级 static——任何跨进程或并发场景都无法支持

### 2.2 跨平台兼容性：★★★☆☆（中等，有关键阻塞项）

**已做的跨平台准备：**
- 目标框架 `net10.0`（非 Windows 专属 TFMs）
- `#if HEADLESS` 条件编译隔离
- `System.Drawing.Common` 已移除
- `WindowsConsoleHelper` 中 P/Invoke 调用全部有 `OperatingSystem.IsWindows()` 守卫
- VT 终端渲染理论上在 Linux/macOS 终端可用

**关键阻塞项：**

1. **`[STAThread]` 注解**：[Program.cs#L19](../../EraCore.Core/Program.cs#L19) — .NET 10 在非 Windows 上忽略此属性，不会报错但属于语义噪音，暗示曾有 COM/OLE 依赖残留

2. **Win32 P/Invoke 密集**：`WindowsConsoleHelper.cs` 包含 6 个 `DllImport("kernel32.dll")`，虽有守卫但 `DetectConsoleFont()` 的 `CreateFileW` + `GetCurrentConsoleFontEx` 在非 Windows 上是死路径——字符宽度探测将完全失效

3. **Win32ConsoleInterop.cs**：`Terminal/` 目录下的 `Win32ConsoleInterop.cs` 名字即暗示 Windows 专用，CLI VT 模式在 Linux 上可能无法启动

4. **HttpListener 局限**：`HttpGameServer.cs#L26` 使用 `HttpListener`，在 Linux/macOS 上需额外配置或 libcurl 依赖，且 .NET 10 对非 Windows 的 HttpListener 支持有限

5. **终端尺寸控制**：`WindowsConsoleHelper.TrySetConsoleSize()` 在非 Windows Terminal 下使用 `Console.BufferWidth`/`Console.WindowWidth`，这些 API 在 Linux 上行为不一致

### 2.3 可扩展性：★★★☆☆（中等）

**做得好的：**
- Agent 协议可扩展：新增协议只需继承 `AgentProtocolBase`
- SessionIO 可扩展：新增 WebSocket 传输只需实现 `SessionIO` 的 4 个方法
- 按钮区域追踪 [ButtonRegionTracker](../../EraCore.Core/Agent/ButtonRegionTracker.cs) 已独立为可测试组件

**瓶颈：**

1. **GlobalStatic 单会话硬约束**：注释明确写了"不支持并发多会话"——如需支持多前端同时连接同一游戏实例，或者一个进程跑多个游戏，这是最大障碍。虽然当前单会话是预期设计，但跨平台前端（Web/App/TUI）可能需要至少"多观察者单控制器"模式

2. **EmueraConsole ↔ GlobalStatic 循环依赖**：EmueraConsole 的 `IsWaitingEnterKey` 属性直接写 `GlobalStatic.ForceQuitAndRestart = false`（[L112-L118](../../EraCore.Core/UI/Game/EmueraConsole.cs#L112-L118)），游戏引擎与全局状态紧耦合，无法独立实例化

3. **HeadlessConsole 的 `Invoke` 实现**：[HeadlessConsole.cs#L24](../../EraCore.Core/Headless/HeadlessConsole.cs#L24) `Invoke(Action)` 直接同步执行，这在单线程 CLI 模式下没问题，但若未来引入异步 UI 框架（如 Web 前端），需要真正的调度器

4. **JSONL turn 结构硬编码**：[AgentJsonlProtocol](../../EraCore.Core/Agent/AgentJsonlProtocol.cs) 的 `BuildTurn()` 使用匿名对象序列化，缺乏版本化和 schema 管理——跨平台前端对接时容易因字段变更而断裂

### 2.4 代码质量：★★★★☆（良好）

**优势：**
- `TreatWarningsAsErrors` + `Nullable enable` + `EnableNETAnalyzers`——质量护栏已到位
- 命名规范统一，中文注释充分
- 异常处理策略明确：脚本运行期异常一律 fatal（[AgentJsonlProtocol.cs#L54-L56](../../EraCore.Core/Agent/AgentJsonlProtocol.cs#L54-L56)）
- `GameExitException` 作为控制流异常语义清晰
- Session 的 `finally` 块确保 `GlobalStatic.Reset()` 被调用（[Session.cs#L61-L96](../../EraCore.Core/Server/Session.cs#L61-L96)）

**问题：**
- `Shared/` 子树通过 `.editorconfig` 抑制历史警告——技术债务被有意封存但未清零
- [AgentCliProtocol.cs](../../EraCore.Core/Agent/AgentCliProtocol.cs) 441 行且包含嵌套类 `LoopStrategy`/`VtLoopStrategy`/`ConsoleKeyLoopStrategy`，职责过重
- `EmueraConsole` 的属性暴露模式（直接委托 `_state` 的 public 字段）打破了封装，未来重构 `_state` 时影响面大

### 2.5 性能：★★★★☆（良好）

- `Channel.CreateUnbounded` + async/await 全异步链路，无阻塞轮询
- Agent 轮询用 50ms 间隔 + 30s 超时，CPU 占用合理
- `ServerGarbageCollection=true` 适合服务端场景
- TINPUT 超时通过 `CancellationTokenSource.CancelAfter` 实现，无定时器泄漏

**潜在问题：**
- `WaitForInputAsync` 的轮询模式（[AgentJsonlProtocol.cs#L189-L200](../../EraCore.Core/Agent/AgentJsonlProtocol.cs#L189-L200)）在游戏长时间运行（如 WAIT 命令）时会产生持续 50ms 间隔的空轮询——可考虑改用事件信号

## 三、风险分析

| 风险 | 严重度 | 概率 | 说明 |
|------|--------|------|------|
| 非 Windows 平台 CLI 模式完全不可用 | **高** | **高** | VT 输入/字体探测/终端控制全部依赖 Win32 API |
| 非 Windows 平台 Server 模式功能降级 | **中** | **中** | HttpListener 在 Linux 上可用但不稳定；字符宽度探测缺失 |
| GlobalStatic 阻碍多前端接入 | **中** | **低** | 当前单会话够用，但 Web 前端可能需要多观察者 |
| Shared 子树债务泄漏 | **低** | **中** | .editorconfig 封存有效，但逐步收紧时会暴露大量警告 |
| JSONL turn schema 无版本化 | **中** | **中** | 前端对接时字段变更会静默断裂 |

## 四、重构计划

### 优先级 P0：跨平台基础能力

#### 1. 终端抽象层提取

**目标**：将 `WindowsConsoleHelper` 和 `Win32ConsoleInterop` 拆为平台抽象

**方向**：
- 定义 `ITerminalPlatform` 接口：`TryEnableAnsi()` / `DetectCharWidths()` / `SetConsoleSize()` / `DetectFont()`
- 实现 `WindowsTerminalPlatform`（现有 P/Invoke）和 `PosixTerminalPlatform`（使用 `\x1b[>` 序列 + terminfo/`stty size`）
- `TerminalDisplayWidth.DetectCharWidths()` 改为委托 `ITerminalPlatform`

**预期改进**：CLI 模式可在 Linux/macOS 终端工作

**涉及文件**：
- `WindowsConsoleHelper.cs` → 拆分为 `ITerminalPlatform.cs` + `WindowsTerminalPlatform.cs` + `PosixTerminalPlatform.cs`
- `Win32ConsoleInterop.cs` → 功能并入 `WindowsTerminalPlatform`
- `AgentCliVtInput.cs` → `WindowsVtInput` 提取为平台策略

#### 2. HTTP 服务器替换为 Kestrel

**目标**：替换 `HttpListener`，获得跨平台 HTTP + 未来 WebSocket 能力

**方向**：
- 添加 `Microsoft.AspNetCore.App` 框架引用（或最小化 Kestrel 包）
- `HttpGameServer` → `KestrelGameServer`，保持相同的路由与 handler 逻辑
- `Session`/`SessionIO` 层不变，只替换传输层

**预期改进**：Server 模式在 Linux/macOS 上开箱可用；为 WebSocket 支持铺路

**涉及文件**：
- `HttpGameServer.cs` → 重写
- `ServerRunner.cs` → 适配 Kestrel 启动
- `Emuera.Headless.csproj` → 添加 Kestrel 依赖

### 优先级 P1：可扩展性增强

#### 3. Turn 协议版本化与 Schema 定义

**目标**：JSONL turn 结构可演进，前端可版本协商

**方向**：
- 定义 `TurnSchema` record，替代 `BuildTurn()` 中的匿名对象
- 添加 `protocolVersion` 字段到初始握手
- 考虑引入 Source Generator 生成序列化代码（避免反射开销）

**涉及文件**：
- `AgentJsonlProtocol.cs` → `BuildTurn()` 重构
- `JsonlCommand.cs` → 添加版本字段

#### 4. IConsoleUI.Invoke 调度器抽象（已取消）

**目标**：支持异步 UI 框架

**方向**：
- `IConsoleUI` 添加 `Task InvokeAsync(Func<Task>)` 方法
- `HeadlessConsole.Invoke` 保持同步直接执行（单线程 CLI）
- 未来 Web 前端实现可注入 `SynchronizationContext` 或 `Dispatcher`

**涉及文件**：
- `IConsoleUI` 接口 → 添加方法
- `HeadlessConsole.cs` → 实现新方法
- `AgentProtocolBase.DispatchInput` → 改为异步路径

**取消理由**：原前提"未来 Web 前端实现可注入 `SynchronizationContext`"假设前端
与 Headless 同进程。实际架构采用 HTTP/JSON 协议解耦（`KestrelGameServer` +
`HttpSessionIO`）：Web 前端是独立进程，通过 `/turn` / `/input` 端点与 Headless
通信，不直接调用 `IConsoleUI`。`IConsoleUI` 在 Headless 模式下永远是
`HeadlessConsole` 空实现，游戏引擎仍单线程跑，同步 `Invoke(Action)` 已满足需求。
前端自身的异步 UI 调度由前端框架处理，与 Headless 无关。详见
[TODO.md 已取消区](./TODO.md#已取消)。

### 优先级 P2：代码质量提升

#### 5. EmueraConsole 门面瘦身

**目标**：减少 EmueraConsole 的公开表面，提高可维护性

**方向**：
- 将 30+ 属性按职责分组到 `IConsoleState`/`IConsoleInput`/`IConsolePrint` 只读接口
- Agent 层只依赖所需的最窄接口
- `_state` 字段改为 `internal` 且仅子对象可访问

**涉及文件**：
- `EmueraConsole.cs` → 接口提取
- `AgentProtocolBase.cs` → 改为依赖窄接口
- `AgentJsonlProtocol.cs` → 同上

#### 6. Shared 子树债务清零（渐进）

**目标**：逐步移除 `.editorconfig` 对 `Shared/**` 的警告抑制

**方向**：
- 按 T-022 计划逐步修复 nullable 警告
- 每次修复一个子目录，配合 CI 验证
- 最终目标是全项目 `Nullable enable` + `TreatWarningsAsErrors` 无抑制

#### 7. AgentCliProtocol 拆分

**目标**：441 行的 CLI 协议类拆分为可维护的小组件

**方向**：
- `LoopStrategy` 及其子类提取为独立文件
- VT 模式管理逻辑提取为 `VtSessionManager`
- 按钮选择/超时渲染已有独立类，但创建和组装逻辑仍在构造器中——可提取工厂

## 六、结论

当前架构的核心设计——Agent 协议抽象、IConsoleUI 空实现、SessionIO 可插拔 IO——是**正确且健壮的**。最大的短板不是设计缺陷，而是**跨平台基础设施的缺失**：终端操作全绑 Win32、HTTP 服务器用 HttpListener。这两项不解决，跨平台前端开发就无从谈起。

好消息是，这些阻塞项都是**局部替换**而非架构重组。P0 阶段只需改 `WindowsConsoleHelper` 和 `HttpGameServer` 两个组件，协议层和游戏引擎层完全不用动。这说明当前分层架构的隔离效果确实在发挥作用——即使我对此并不感到特别惊讶。

下一步建议从 P0-2（Kestrel 替换）开始，因为它同时解决跨平台 HTTP 和未来 WebSocket 支持，投入产出比最高。
