# 2026.8.25 游戏退出后内存不释放 —— 排查流程与方法论

> 状态：阶段性修复完成（进程内存 472MB → 208MB），**仍有残留，待更彻底排查**
> 涉及：EraCore.Maui（壳）+ EraCore.Core（共享运行时）的静态根持有分析
> 复现工具：MAUI Windows Debug（AllocConsole）+ dotnet-counters + dotnet-dump

---

## 一、现象与目标

MAUI 应用打开游戏后退出，进程内存几乎不变（打开游戏 472MB → 退出后仍 ~472MB），
预期应回落到接近启动值（~47MB）。

**注意**：任务管理器看到的"进程内存"是工作集/私有字节的混合体，不能直接反映托管堆。
必须用托管堆指标（`GC Heap Size` / `Gen 2 Size` / `LOH Size`）区分"真泄漏"与"GC 机制保留"。

---

## 二、排查流程（三步法，可复用于同类问题）

### 第 1 步：区分「真泄漏」与「GC 机制」

```bash
dotnet-counters monitor --counters System.Runtime --process-id <PID>
```

关键指标与**陷阱**：

| 指标 | 含义 | 陷阱 |
|---|---|---|
| `dotnet.gc.heap.total_allocated` | 进程累计分配字节数 | **只增不减，永不下降**——不能用于判断内存释放，仅算分配速率 |
| `last_collection.heap.size`（gen0/1/2/loh） | **最近一次 GC 结束时**各代堆大小 | 是"某次 GC 时的快照"，若主动 GC 未执行/未看，数字是旧的 |
| `Gen 2 Size` / `LOH Size` / `GC Heap Size` | 当前堆大小（GC 后） | 主动 GC 完成后看，才有意义 |
| `last_collection.memory.committed_size` | 已提交堆内存 | 即使对象回收，GC 默认不把 Gen2 堆段归还 OS（峰值段保留），此值可能不降 |

判定：
- 托管堆（Gen2+LOH）退出后不降 → **真泄漏**（有静态根/事件/AsyncLocal 钉住对象图）
- 托管堆降、但进程内存不降 → **GC 机制**（堆段保留 + JIT 代码 + 框架常驻，属正常）

实测结论：退出后 Gen2 116MB + LOH 61MB ≈ 177MB 存活 → **真泄漏**。

### 第 2 步：代码静态根审查（首轮，有效但不够）

全局搜索静态字段持有引擎对象的模式，命中并修复：

```csharp
// GlobalStatic.Scope.Dispose（游戏循环唯一出口）挂接的清理链
ParserMediator.ClearWarningList();
ParserMediator.Initialize(null);          // static EmueraConsole → Process 整图
PluginManager.ResetInstance();            // 静态单例 → Process/ExpressionMediator/VariableData wrapper
PluginAPICharContext.ClearStaticCache();  // 27 个静态 VariableToken + exm
StrForm.ClearStaticCache();               // 5 个静态 FunctionMethodTerm（格式化）
VariableParser.ClearStaticCache();        // 静态 VariableTerm TARGET/ZeroTerm
AppContents.UnloadContents();
Preload.Clear();
ConsoleEscapedParts.Clear();
```

**结果**：每轮清理都让进程内存降 ~28MB，但 Gen2 116MB 纹丝不动——说明是**多条静态根链**，
代码审查无法穷举。必须用 dump 定位。

### 第 3 步：dotnet-dump gcroot 迭代定位（决定性方法）

```bash
dotnet tool install -g dotnet-dump
dotnet-dump collect -p <PID> -o exit.dmp          # 退出游戏后收集
dotnet-dump analyze exit.dmp
> dumpheap -stat                                   # 看最大类型（定位大头在哪）
> dumpheap -type <类型名> -short                   # 拿一个实例地址（输出海量地址属正常，取第一个）
> gcroot <地址>                                     # 看完整引用链：根 → ... → 对象
```

`gcroot` 输出解读：`(static variable: X)` 表示 **X 静态字段**持有链上第一个对象；
三条 Thread 根通常都指向同一静态字段（.NET 静态字段存在类型加载器堆，寄存器只是碰巧引用）。

**三轮迭代各揪出一个静态根**：

| 轮次 | gcroot 定位的根 | 来源 | 修复 |
|---|---|---|---|
| 1 | `FunctionMethodTerm.NameAssi` | `StrForm.Initialize()`（Process.cs:597）用当前游戏 `VariableData` token 构造 5 个静态格式化缓存（`%TARGET%`/`///` 三元符号） | `StrForm.ClearStaticCache()` |
| 2 | `SingleTerm.<ZeroTerm>k__BackingField` | `VariableParser.Initialize()`（Process.cs:598）静态 `TARGET`（VariableTerm → 运行时 token） | `VariableParser.ClearStaticCache()` |
| 3（代码审查发现，未等 gcroot） | `PluginManager` 静态单例 + `PluginAPICharContext` 静态 token | `Process.Initialize`（Process.cs:603）`SetParent` **无条件**缓存 Process/ExpressionMediator/约 50 个 VariableData wrapper | `PluginManager.ResetInstance()` + `PluginAPICharContext.ClearStaticCache()` |

## 三、关键架构发现（同类问题的一劳永逸排查法）

**泄漏模式**：引擎在 `Process.Initialize`（**每次游戏加载**都会执行）用**当前游戏会话的
VariableData token** 构造"静态缓存"——静态字段 → `VariableTerm`/`VariableToken` →
`VariableData` → `ConstantData` → `EmueraConsole` → `Process`（LabelDictionary/CSV/变量表）
整张对象图。会话结束只清 AsyncLocal（`GlobalStatic.Current = null`），这些静态根仍指向旧图。

**系统性排查清单（Core 全量）**：
1. `public/internal static void Initialize()` 全库搜索 → 只有 ParserMediator / StrForm / VariableParser 三处（全部覆盖）
2. 静态字段类型为 `VariableTerm` / `FunctionMethodTerm` / `SingleTerm` / `VariableToken` → 只有 StrForm / PluginAPICharContext / VariableParser 三处（全部覆盖）
3. 静态单例模式（`static ... GetInstance()`）→ 只有 PluginManager（已覆盖）；AgentLog 为日志单例不持有运行时，无需清
4. `static event` → Core 内无
5. 注意 `Emuera\GlobalStatic.cs` 是 WinForms 版（真正的 static 字段），MAUI 用 Core 的 AsyncLocal 版，不参与编译——别改错文件

**清理设计原则**：
- 统一挂 `GlobalStatic.Scope.Dispose`（游戏循环唯一出口，`GameLoopComposer.RunAsync` 的 using 块），一处收口覆盖 CLI/Server/MAUI 全宿主
- 每次游戏加载都会重建（`Process.Initialize` 重调各 `Initialize()`），清空无需手动恢复
- 有插件游戏退出时统一清理；**无插件游戏启动时即回收**（`Process.Initialize` 检测 `HasPlugins == false` → 立即 `ResetInstance`）

## 四、修复成果

| 指标 | 打开游戏 | 退出后（修复前 → 修复后） |
|---|---|---|
| 进程内存 | 472MB | ~472MB → **208MB** |
| LOH | ~64MB | ~61MB → **~44MB** |
| Gen2 | 116MB | 116MB（逐步修复中） |

另：主动 GC（`GC.Collect(2, Forced, compacting)` + `WaitForPendingFinalizers` + 二次收集，
`BridgeHost.Dispose` 的 host.Dispose 完成后后台线程执行，Preferences key `app.activeGcOnExit` 默认 true）
用于把已释放对象的内存段归还 OS，让任务管理器数字可见回落。

## 五、未完成 / 待排查方向（208MB 剩余）

退出后 208MB - 启动 47MB ≈ 161MB 组成待细分：
1. **.NET Gen2/LOH 峰值堆段保留**（设计行为，峰值 ~420MB 堆的段只归还一部分）
2. **JIT native 代码**（ERB/CSV 解析执行代码量大，13k+ 方法，常驻不归 GC 管）
3. **MAUI/WinUI 框架 + WebView2 进程内组件** 常驻
4. **可能仍存在的静态根**（本轮穷举了 VariableTerm 类静态字段，但未穷举：AsyncLocal 捕获、
   事件订阅、`ImageNameTable._map` 静态 sprite 表、`FontFactory.fontDic` 等未清项）

**下一步更彻底排查的路径**：
- 再跑一轮 `dumpheap -stat` + `gcroot`，若 Gen2 仍高，定位下一个根
- 重点检查 **AsyncLocal 上下文捕获**：scope 打开期间创建的、scope 外存活的对象
  （`System.Threading.Timer`、MAUI `Dispatcher.Dispatch` 投递的委托、跨 Task 的 await 链）
  会捕获 `GlobalStatic.Current`（AsyncLocal 值快照），即使 `_current.Value = null` 后仍持有旧 scope
  → scope 实例 → `_console`/`_process`/`_variableData` 整图
- 对比实验：退出后立即 dump vs 等待 1 分钟再 dump，观察 Gen2 是否随时间下降（终结点/后台清理）
- 若确认是"堆段保留 + JIT + 框架"（托管堆已降干净），剩余部分为 .NET 机制，可接受或进一步调
  `DOTNET_GCHeapHardLimit` / Server GC 配置

## 六、工具命令备忘

```bash
# 托管堆观测（区分真泄漏 vs 机制）
dotnet-counters monitor --counters System.Runtime --process-id <PID>
# 指标：GC Heap Size / Gen 2 Size / LOH Size（total_allocated 是累计值勿用）

# 堆快照 + 引用链定位（gcroot 是决定性手段）
dotnet tool install -g dotnet-dump
dotnet-dump collect -p <PID> -o exit.dmp
dotnet-dump analyze exit.dmp
> dumpheap -stat
> dumpheap -type MinorShift.Emuera.Runtime.Script.Statements.InstructionLine -short
> gcroot <地址>

# 构建/回归（构建类命令在外部终端执行）
dotnet test EraCore.Tests -c Debug
dotnet run --project EraCore.Maui/EraCore.Maui.csproj -f net10.0-windows10.0.19041.0
```

**过程中踩过的坑**：
1. `total_allocated` 是累计值，永不下降——不能用来判断内存释放
2. `last_collection.heap.size` 是"最近一次 GC 时"快照——主动 GC 未执行时数字是旧的
3. `GC.Collect(2, GCCollectionMode.Optimized, true, blocking: true)` 会报 CS1744（blocking 与位置参数重复）——全部用命名参数
4. `GCSettings`/`GCLatencyMode` 在 `System.Runtime` 命名空间，需 `using System.Runtime;`
5. **SafIoPolicyTests 是行号基线**：在含裸 I/O 的文件头部插入代码会把豁免行号推后导致测试失败——新方法放文件末尾
6. `ConsoleEscapedParts` 静态 DataTable 被并行测试并发访问会抛 `Collection was modified`——加同一把静态锁
7. Core 开启 NRT 且警告提升为错误：`ParserMediator.Initialize(null)` 需把参数改可空（`EmueraConsole?`）而非 `null!` 硬转
